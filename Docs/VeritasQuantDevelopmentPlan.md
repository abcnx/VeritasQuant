## 2. 项目目标与范围控制

### 2.1 可交付目标

1. 建立无未来信息、跨平台可复现的严格事件驱动回测内核。
2. 对每笔成交、部分成交、基金确认及资金变化执行不可变复式记账，并可从空投影重放。
3. 支持同一运行内多个相互隔离的回测、模拟、券商仿真或实盘账户。
4. 支持理想执行与真实执行双轨评估、订单全生命周期、基础风控、风险预警和交易控制。
5. 支持基金净值数据、基金申购赎回、六类内置智能定投方案、日频三种金额模式及用户自定义 DSL 回测。
6. 提供统一 FastAPI 服务、Streamlit GUI、命令资源、结构化日志、审计、监控、调度和报告。
7. 依次通过历史回测、模拟盘、信号参考、券商仿真和小规模实盘 Gate，禁止越级上线。

### 2.2 首期范围

- 阶段 1 只承诺单机分钟 Bar 严格回测，并以 `518880` 和 manifest 指定的单一上期所黄金期货交割合约验证证券与期货能力。
- `MVSV-1` 导入器必须兼容仓库样本，但样本 NVDA 不代表阶段 1 已开放美股交易能力。
- 境内开放式基金和智能定投历史回测在阶段 2 开放；其他批次 B/C/D 资产按能力清单逐项启用。
- 实盘默认关闭，只有阶段 5 批准的账户、标的、策略版本和额度才能被白名单启用。
- 初期不提前建设多区域、复杂微服务或机器学习平台；相关基础设施只在业务链路和 Gate 确有需要时引入。

### 2.3 不可妥协的完成条件

- 统一事件时间字段为 UTC `ts`；同一运行统一使用 `Second` 或 `Millisecond`，禁止隐式降精度。
- 全序键固定为 `ts + phase + priority + source_rank + source_sequence + event_id`，并记录排序版本。
- 当前 Bar 产生的订单不能在当前 Bar 成交；策略不能读取未消费数据、系统时间或未来数据。
- 任何账户状态变化必须来自已提交 journal；历史 journal 只能冲正，不能修改或删除。
- `RiskEngine` 是风险决定和交易控制的唯一发布者；策略、预警、通知和 GUI 均不能绕过风控。
- REST JSON 使用 `ResponseEnvelopeV1`。顶层 `code`、`message` 必填；错误对象固定包含 `error.code`、`error.catalog_version`、`error.retryable`。
- 每次运行记录数据、配置、代码、策略、风险、执行模型、随机种子、时间精度和排序版本。
- 平台正确性 Gate 与策略绩效 Gate 分开；平台错误不能以策略盈利豁免。

### 3.2 估算与容量

- 任务估算使用有效人日，不含等待外部数据、观察窗口和审批时间；`1 人日 = 8 小时`。
- 迭代固定为 2 周。每人每迭代只承诺 7 人日计划工作，预留 20% 处理缺陷/风险、10% 处理评审/支持。
- 超过 10 人日的任务进入迭代前必须继续拆分；超过 2 个工作日仍未定位的技术探索转为有时限的 Spike。
- 每个阶段保留约 15% 管理缓冲，仅由项目负责人用于已登记风险，不能提前消耗以承接新增范围。
- 60/20 个交易日等观察窗口是 Gate 证据窗口，不是可压缩的开发工期。

## 6. 任务准入与完成定义

### 6.1 Definition of Ready

任务进入 `Ready` 前必须满足：

- [ ] 有唯一任务 ID、所属阶段、技术方案章节和业务价值。
- [ ] 内容边界、非目标、输入输出、依赖和责任人明确。
- [ ] 验收标准可自动验证或有明确人工签署人。
- [ ] 涉及事件/API/配置/数据库/DSL 时已完成兼容性和迁移分析。
- [ ] 涉及资金、订单、风险、实盘或敏感数据时已完成安全/失败模式分析。
- [ ] 估算不超过 10 人日；更大工作已拆分。
- [ ] 所需测试数据、外部环境和权限已准备，或等待时间已显式标注。

### 6.2 Definition of Done

任务只有同时满足以下条件才为 `Done`：

- [ ] 实现与技术方案一致，无未经批准的范围扩张。
- [ ] 代码经过至少一名非作者评审；关键账本、风控、执行和安全代码经过领域负责人评审。
- [ ] 单元、契约及最小相关集成测试通过；新增行为有正例、反例和边界测试。
- [ ] 静态类型、格式、依赖边界、安全、命名和 UTF-8 检查通过。
- [ ] 日志、指标、错误码、审计和故障行为已实现并验证。
- [ ] 配置、Schema、数据库或 API 变化具备版本、兼容策略、迁移和回滚方案。
- [ ] 文档、运行手册和追踪矩阵已更新。
- [ ] CI 证据、测试种子、报告、产物和 SHA-256 已关联到任务。
- [ ] 验收人按标准签署，且不存在未登记的遗留问题。

## 7. 进度管理与偏差控制

### 7.1 管理节奏

| 周期 | 活动 | 必须输出 |
| --- | --- | --- |
| 每日 | 15 分钟同步；更新任务状态、剩余量、阻断和新风险 | 当日状态、阻断责任人、下一动作和预计解除时间 |
| 每周 | 关键路径、风险、缺陷、容量、外部依赖复核 | 周报、风险变化、里程碑预测日期、证据完整率 |
| 每两周 | 计划、实现、演示、验收和回顾 | 迭代目标达成率、验收任务、未完成原因、改进行动 |
| 每月 | 架构、质量、SLO、安全和预算审查 | 趋势图、技术债、容量预测、是否调整阶段基线 |
| Gate 前 | 独立证据审计和 Go/No-Go | StageGateReport、开放风险例外、唯一结论与签名 |

### 7.2 强制进度指标

| 指标 | 计算口径 | 绿色 | 黄色 | 红色及动作 |
| --- | --- | ---: | ---: | --- |
| 验收完成率 | 已验收任务人日/基线计划人日 | >=95% | 85%-94% | <85%，3 日内提交恢复计划 |
| 里程碑进度指数 SPI | 已验收价值/计划价值 | >=0.95 | 0.85-0.94 | <0.85 或连续两周 <0.9，重估关键路径 |
| 范围变动率 | 迭代开始后新增或变更人日/承诺人日 | <=5% | 5%-10% | >10%，触发变更控制并保护迭代目标 |
| 估算偏差 | 实际人日/估算人日 | 0.8-1.2 | 1.2-1.5 | >1.5，拆分根因并修正同类估算 |
| 阻断老化 | 阻断状态连续工作日 | <=2 日 | 3-5 日 | >5 日，升级至 PO/TL 并调整依赖 |
| 缺陷逃逸率 | 下一环境发现缺陷/该版本总缺陷 | <=5% | 5%-10% | >10%，暂停晋级并补测试 |
| Gate 证据完整率 | 已有有效证据的强制项/全部强制项 | 100% | 95%-99% | <95% 或任一关键项缺失，结论只能为证据不足 |
| 自动化测试稳定率 | 非产品缺陷导致的通过次数/执行次数 | >=99% | 97%-99% | <97%，隔离不稳定测试并限期修复，禁止静默重跑取绿 |

只有验收完成的任务计入进度；“编码完成”“已提交评审”和“测试中”均不计挣值。迭代 4 之后按历史吞吐每月计算 P50/P85 完成日期，外部承诺使用 P85；若 P85 比基线晚两个迭代，必须通过降非核心范围、增加经验证容量或正式改基线处理。

### 7.3 关键路径与缓冲

关键路径固定为：事件/配置契约 -> 数据版本 -> 事件循环/事务 -> 账本 -> 订单/撮合 -> 风控 -> 策略/报告 -> 阶段 1 Gate -> 多账户持久化 -> 模拟盘 60 日 -> 信号 20 日 -> 券商仿真 20 日/100 单 -> 实盘准备 -> 影子 20 日。

- 关键路径任务不得同时分配给超过 2 个未完成工作项的负责人。
- 阶段缓冲消耗达到 33%/66%/100% 时分别标记黄/橙/红，并提高周审频率。
- 观察窗口中断是否重置由冻结的 Gate Policy 决定，不能在结果出现后临时解释。
- 外部券商、数据许可和实盘账户申请至少提前两个阶段启动，但未满足技术 Gate 前不得接入生产主链路。

## 8. 风险、突发问题与复盘数据

### 8.1 强制登记规则

任何可能影响范围、日期、资金正确性、交易安全、数据可信度或 Gate 的风险与突发问题都必须在发现当日登记。口头同步、聊天记录和日志告警不能代替正式记录。记录至少包含：

- 唯一 ID、发现 `ts`、发现人、来源任务/版本/环境。
- 事实描述、已知影响、未知项和禁止推测的部分。
- 概率、影响、风险暴露、严重度、触发器和受影响里程碑。
- 唯一责任人、协作人、下一动作、截止时间和升级时间。
- 规避/缓解措施、应急预案、残余风险和批准人。
- 关联需求、PR、配置、运行、事件、账户、日志、指标、trace、测试和产物哈希。
- 状态变化时间线、每次决策依据、验证结果和关闭证据。

风险状态使用 `IDENTIFIED -> ANALYZING -> MITIGATING -> MONITORING -> CLOSED/ACCEPTED`。突发问题使用 `DETECTED -> TRIAGED -> CONTAINED -> RESOLVING -> VERIFYING -> CLOSED`。风险被接受必须有到期日和批准人，不能永久搁置。

### 8.2 响应时限

| 等级 | 示例 | 首次确认 | 完成分诊 | 升级与处置 |
| --- | --- | ---: | ---: | --- |
| S0 | 未授权实盘、资金/账本不可恢复、保护动作失效 | 5 分钟 | 15 分钟 | 立即停止相关交易，通知 PO/TL/SRE，持续指挥至受控 |
| S1 | 重复下单、跨账户串扰、未解释对账差异、未来数据泄漏 | 15 分钟 | 30 分钟 | 阻断发布/晋级，2 小时内形成遏制与证据保全方案 |
| S2 | 主要功能不可用、里程碑关键路径受阻、SLO 严重违约 | 2 小时 | 1 工作日 | 当日指定恢复计划，周报单列 |
| S3 | 局部缺陷、非关键偏差、可控技术债 | 1 工作日 | 2 工作日 | 纳入最近迭代或经批准排期 |

### 8.3 证据保全与事后复盘

突发问题发生后必须生成只读证据包，至少包含：

1. 原始告警、结构化日志、指标快照和 trace，统一 UTC 时间线。
2. 相关运行清单、代码/配置/数据/Schema/策略/镜像版本和哈希。
3. 事件、命令、inbox/outbox、订单迁移、执行回报、journal、控制与对账记录。
4. 故障前后资源、队列、磁盘、数据库、网络和券商状态快照。
5. 所有人工命令、审批、沟通决策、恢复步骤和验证输出。
6. 可复现输入、随机种子、最小失败样本和修复前后测试结果。

S0/S1 在恢复后 5 个工作日内完成无责复盘，S2 在 10 个工作日内完成。复盘必须量化检测时间、确认时间、遏制时间、恢复时间、影响账户/订单/金额/数据范围、SLO/错误预算消耗、根因和促成因素。行动项必须有唯一 ID、责任人、截止日和验证方法；所有 S0/S1 行动项关闭前不得通过下一环境 Gate，除非风险接受由 PO、TL 和安全负责人共同签署且有明确到期日。

## 9. 质量、测试与证据计划

| 层级 | 每次提交 | 每日 | 每迭代 | 阶段 Gate |
| --- | --- | --- | --- | --- |
| 静态检查 | 格式、类型、命名、编码、依赖边界、秘密 | 全量依赖/漏洞增量 | 工具版本和规则复核 | 0 未处理阻断 |
| 单元/契约 | 受影响测试必跑 | 全量快速集 | 全量及覆盖率趋势 | 强制契约 100% 有结果 |
| 属性/模型 | 变更模块固定种子冒烟 | 中等样本 | 至少 10,000 组阶段相关序列 | 失败样本 0，种子归档 |
| 集成/崩溃 | 受影响链路 | 核心链路 | 全边界故障注入 | 事实无丢失/重复，恢复达标 |
| 回归/checksum | 受影响基准 | 主分支固定样本 | Windows/Linux 全量 | 所有变化有批准依据 |
| 安全/打包 | 快速扫描、wheel 冒烟 | 漏洞数据库更新 | 仓库外安装、沙箱探针 | 高危漏洞和越权路径为 0 |
| SLO/运行 | 不适用 | 当前环境趋势 | 错误预算复核 | 满足对应观察窗口与阈值 |

测试被跳过、因环境失败未执行或产物哈希缺失都不能计为通过。随机测试失败必须保存最小化样本并加入固定回归集。基准 checksum 的任何变化必须关联设计变更或缺陷修复，记录旧值、新值、影响分析和批准人。

## 10. 变更、版本与发布控制

1. 新需求先登记并进行影响分析，不能直接插入开发中任务。
2. 改变架构、事件、排序、账户、风险、执行、API、配置、DSL 或持久化语义时，先更新技术方案和版本策略。
3. 变更记录必须给出范围、人日、关键路径、测试、迁移、回滚和 Gate 影响。
4. 迭代内仅 S0/S1 修复或经 PO/TL 批准的阻断变更可打断承诺；其他变更进入下次规划。
5. 基线调整保留原日期、原工作量和原因，发布新 `PlanVersion`，禁止覆盖历史数据。
6. 发布工件必须包含 wheel/镜像、依赖锁、配置/Schema/错误目录、迁移、SBOM、测试报告、运行清单模板和 SHA-256。
7. 环境晋级只部署同一不可变工件；配置差异通过版本化外部配置表达，禁止在目标环境现场改代码。

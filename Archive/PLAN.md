# 严格事件驱动量化策略交易平台深度规划方案

---

## 1. 概述与目标

本方案设计一套支持多策略、多标的、跨市场的量化交易平台。标的范围覆盖黄金期货（沪金/COMEX）、黄金ETF（518880/GLD）、黄金矿股ETF（GDX）、黄金现货（AU9999/国际金）、积存金、A股/港股/美股个股、国内ETF、港股ETF及QDII基金。平台以**分钟级历史行情文件**为主要初始数据源，交易频率覆盖小时级到日级，并在严格“无未来信息”的事件驱动机制下运行，确保回测结果高度可信。

方案遵循“一次编写，逐级验证”的核心理念，通过五个里程碑阶段渐进演进：
- **第一阶段**：基于历史数据的严格回测验证
- **第二阶段**：基于后续采集的实盘历史数据的模拟盘跟踪
- **第三阶段**：生成/输出交易操作信号供人工参考
- **第四阶段**：间隙式接入仿真验证、实盘数据复盘修正与后训练调优
- **第五阶段**：全自动实盘运行

核心挑战与应对：
- **绝对禁止未来信息**：流式读取文件，逐分钟推进，订单用下一分钟Bar价格撮合。
- **交易影响不可逆**：每笔成交即时更新资金与持仓，后续决策完全依赖最新状态。
- **成交不确定性模拟**：可配置的多层级概率撮合模型，涵盖延迟、排队、部分成交、滑点等。
- **异构事件支持**：架构天然支持行情之外的新闻、政策、宏观指标、极端事件等广义事件，并保障回测与实盘一致性。

## 2. 核心设计原则

### 2.1 严格因果时序
引擎以分钟Bar为最小时间原子，事件处理顺序严格固定：接收分钟Bar → 撮合待成交订单 → 将Bar推送给策略 → 策略生成新订单。所有状态更新单向不可逆，杜绝任何形式的前视。

### 2.2 流式数据消费
历史行情文件按时间逐行读取，已消费数据立即释放。策略只能通过自身维护的窗口访问已发生事件，无法调用全局预加载函数。

### 2.3 交易状态实时固化
每一笔成交（或部分成交）立即改变账户资金、持仓、已实现盈亏。策略在任何时点获取的账户信息均为最新，下单规模与风控决策基于当前真实可用资源。

### 2.4 策略与执行解耦
策略仅产生信号（`OrderEvent`），执行器独立负责订单管理、撮合与成交回报。策略代码在不同运行模式（回测、模拟、仿真、实盘）中完全不变，仅通过配置切换执行器。

### 2.5 成交不确定性显式建模
抽象出可配置的多层级撮合模型，模拟实盘中的网络延迟、订单排队、部分成交、滑点和超时撤单，使回测绩效真实反映市场微观结构。

### 2.6 广义事件驱动
系统基于统一事件协议，不仅能处理行情数据，还能无缝接入市场消息、经济指标、政策文件、舆情数据及黑天鹅/灰犀牛等极端事件，使策略具备多维度市场认知能力，并在回测中严格保持无未来信息。

## 3. 系统总体架构

平台采用**事件驱动微内核架构**，由以下核心模块构成：

- **数据网关**：流式读取历史行情文件或接入实时行情，产出 `MarketEvent`；同时可接入异构数据适配器，产生各类 `GenericEvent`。
- **事件总线**：统一事件队列，维护全局时序，将事件按时间顺序分发给订阅者。
- **策略引擎**：管理多策略实例，接收行情与通用事件，输出订单事件。
- **订单队列与撮合引擎**：维护所有未成交订单，实现多层概率撮合模型，产出成交事件。
- **风险控制模块**：在订单链路中多层拦截，进行策略级和全局级检查。
- **持久化与监控**：记录所有事件、订单、成交、账户快照，提供可视化看板与告警。

数据流如下：

```
行情文件 / 实时行情 / 异构数据源
        │
        ▼
 事件生成器 (流式读取，多源归并)
        │
        ▼
   事件总线 (严格按时间排序)
        │
        ▼
   事件循环引擎 (单线程推进)
        │
        ├──> 撮合引擎 (处理待成交订单，使用当前事件价格)
        │        │
        │        ▼
        ├──> 账户/持仓更新 (产生FillEvent)
        │
        ├──> 策略引擎 (接收MarketEvent/GenericEvent)
        │        │
        │        ▼
        ├──> 风险控制 (审核新订单)
        │        │
        │        ▼
        └──> 订单队列 (新订单加入，等待后续撮合)
```

所有模块共享同一逻辑时钟（当前分钟时间戳），保证执行顺序绝对一致。

## 4. 异构事件体系：超越行情的深度市场认知框架

本平台事件驱动架构天然支持除行情数据外的任意异构事件类型。一切能够影响市场状态和策略决策的信息，均被抽象为统一格式的**广义事件**，使策略能对价格之外的新闻、政策、宏观指标、乃至极端事件做出响应。

### 4.1 统一事件协议与基类设计

所有事件继承自通用基类 `Event`：

```python
class Event:
    event_id: str          # 全局唯一ID
    event_type: str        # 事件类型标识符
    timestamp: datetime    # 事件发生时间（UTC）
    source: str            # 来源（如 "reuters", "policy_db"）
    priority: int          # 处理优先级（0低，9最高）
    data: dict             # 具体载荷
```

- **标准化路由**：事件总线根据 `event_type` 将事件分发给订阅该类型的策略或模块。
- **时间一致性**：所有事件携带 `timestamp`，事件循环严格按时间顺序混合处理行情与异构事件，确保因果时序。

### 4.2 异构事件分类与标准化模型

#### 4.2.1 市场资讯类事件

- **新闻/公告事件**  
  类型标识：`news.general`, `news.earnings`, `news.merger`  
  载荷包含关联标的、标题、正文、情绪得分（NLP预计算）、相关性、来源可信度等。  
  接入方式：通过新闻API或爬虫适配器，经NLP处理后注入总线。

- **社交媒体舆情事件**  
  类型标识：`social.tweet`, `social.reddit`  
  捕捉市场情绪突变，适用于短线策略或风险预警。

#### 4.2.2 经济日历与政策事件

- **宏观经济指标发布**  
  类型标识：`macro.cpi`, `macro.gdp`, `macro.nfp`  
  载荷包含实际值、预期值、前值、意外偏离度、重要性评级。  
  接入方式：从经济日历源定时抓取，按公布时刻注入事件流。

- **央行及政策事件**  
  类型标识：`policy.rate_decision`, `policy.speech`  
  包含利率决议、投票分布、鹰鸽倾向等结构化数据。

#### 4.2.3 极端与不可预见事件（黑天鹅/灰犀牛）

- **定义**：  
  - 灰犀牛：高概率、高冲击但常被忽视的事件（如债务危机）。通过宏观预警模型产生信号。  
  - 黑天鹅：极低概率、突发巨大冲击。系统通过复合事件检测器实时生成预警。
- **工程化表示**：  
  类型标识：`alert.extreme_volatility`, `alert.liquidity_dry_up`, `alert.correlation_breakdown`  
  载荷包含预警类型、描述、严重程度、检测规则等。  
  当市场监控模块检测到波动率突破历史极值、流动性枯竭等特征时，立即产生紧急事件，策略可进入避险模式。

### 4.3 回测与实盘中的处理

- **回测模式**：构建与历史行情时间完全对齐的异构事件库。文件流式读取，严格按时间注入，保证无未来信息。支持事件时效半衰期模型。
- **实盘模式**：新闻API、社交媒体流、经济日历提醒、极端事件检测器等作为独立适配器，实时产出 `GenericEvent` 推送至事件总线，与行情归并处理。

### 4.4 策略如何响应异构事件

策略基类增加回调接口：

```python
class BaseStrategy:
    def on_bar(self, bar_event): ...
    def on_tick(self, tick_event): ...
    def on_event(self, event: GenericEvent): ...
    def on_news(self, news_event): ...
    def on_macro(self, macro_event): ...
    def on_alert(self, alert_event): ...
```

- **示例应用**：  
  - 避险策略：接收 `alert.extreme_volatility` 后立即平仓风险资产，转投黄金或国债ETF。  
  - 事件驱动策略：监听 `macro.cpi`，超预期做多美元，做空黄金。  
  - 情绪策略：累积 `news.general` 情绪得分，突破阈值时交易。  
  - 风险控制：`RiskManager` 订阅所有 `alert.*`，强制降仓或增加对冲。

## 5. 数据管理与流式回放机制

### 5.1 行情文件规范
历史行情采用 CSV 或 Parquet 格式，每行一根分钟Bar，字段：
```
datetime, symbol, open, high, low, close, volume, amount
```
文件按标的、年月分目录存放，如 `data/AU8830/2024/01.parquet`，并严格按时间递增排序。日线数据由分钟数据在收盘后自动合成，仅在所有分钟Bar走完后才提供给策略查询。

### 5.2 流式回放器
- 为每个文件维护迭代器，使用最小堆跨文件归并，每次取出时间戳最小的一行作为 `MarketEvent`。
- 读取后立即释放该行，内存中不保留后续数据。
- 支持速率控制：`max`（极速回测）或 `1`（模拟实盘分钟步进）。
- 异构事件库同样采用流式归并，与行情事件统一排序。

### 5.3 日线数据辅助
日线数据在交易日结束后自动生成并存储。策略可在次日开盘后通过 `get_daily_bars(symbol, n)` 获取已完成日线，严禁在当日结束前访问未完成的日数据。

## 6. 严格事件驱动与防未来信息设计

### 6.1 事件循环流程
主循环每次迭代处理一个事件（行情或异构），顺序如下：

1. 取出时间戳最小的事件，设为当前系统时间。
2. **撮合阶段**：用该事件携带的价格信息（若是行情）撮合订单队列中所有符合条件的订单，产生 `FillEvent` 并立即更新账户。
3. **策略决策阶段**：将该事件分发给所有订阅的策略（`on_bar` 或 `on_event`），策略基于最新的账户状态和历史窗口产生 `OrderEvent`。
4. 新订单经风控检查后加入订单队列，**绝不会在本次循环中被撮合**。
5. 持久化所有事件与账户快照。
6. 回到步骤1。

“先撮合、后决策”确保策略在T分钟结束时已看到T分钟之前所有订单的成交结果，但无法用T分钟的价格去撮合自己刚下的单，完美模拟实盘时序。

### 6.2 防作弊机制
- 策略只能通过 `self.data_window` 维护已接收的事件序列，引擎不提供全局历史查询。
- 自动化测试随机注入未来数据检查点，若策略违规引用则立即报错。
- 数据窗口仅允许追加，不允许时间索引超出当前系统时间。

## 7. 策略引擎与多策略管理

### 7.1 策略基类
```python
class BaseStrategy:
    def on_bar(self, bar_event): ...
    def on_event(self, event): ...
    def on_fill(self, fill_event): ...
    def on_partial_fill(self, event): ...
    def on_order_cancelled(self, event): ...
    def create_order(self, symbol, side, quantity,
                     order_type='limit', price=None,
                     timeout=0) -> OrderEvent: ...
```

### 7.2 小时级与日级策略支持
策略在 `on_bar` 中积累分钟Bar，当满足整点或收盘条件时，自行聚合为小时/日线用于信号判断。聚合逻辑完全透明，无未来信息。

### 7.3 多策略管理器
`StrategyManager` 管理多个策略实例，每个策略拥有独立的虚拟分账户和风控参数。行情与通用事件按订阅分发，订单统一经风控和撮合模块处理。绩效独立核算，支持资金隔离与全局控制。

## 8. 实盘成交不确定性模拟与策略应对

实盘中订单存在等待、排队延迟、部分成交或无法成交的风险。若回测假设价格触及即成交，将严重高估绩效。本章详细阐述多层级概率撮合模型及其与策略的交互方式。

### 8.1 成交不确定性的来源
- 网络与系统延迟
- 订单队列优先级
- 流动性不足导致部分成交
- 行情瞬时穿越

### 8.2 多层级撮合模型
系统提供可配置的三层模型，全面模拟实盘撮合过程。

#### 8.2.1 提交延迟（`delay_bars`）
订单生成后延迟指定根数的分钟Bar才进入撮合队列。默认值为1（T分钟订单最早在T+1分钟Bar到达时撮合）。

#### 8.2.2 价格触及判定与排队概率
- 限价单触及条件：买入 `bar.low <= order.price`，卖出 `bar.high >= order.price`（可配置为使用开盘价等）。
- 成交概率模型（可配置）：
  1. **固定概率**：触及后以固定概率 `p_fill` 成交。
  2. **成交量比例**：`P = min(1.0, (bar.volume * participation_rate) / 估计排队量)`。
  3. **历史分布采样**：基于品种历史分钟统计的实际成交概率分布抽样。
- 市价单：无需价格触及，直接成交，但计入冲击成本。

#### 8.2.3 部分成交与订单剩余
- 成交数量不超过该分钟Bar成交量的一定比例（`max_volume_ratio`，默认5%）。
- 剩余数量保留为原订单（限价单）继续等待，或按配置撤销（市价单）。

#### 8.2.4 滑点与冲击成本
- 市价单：成交价 = 当前分钟开盘价 + `slippage_fixed` + `bar.volatility * slippage_ratio`。
- 限价单：按挂单价成交，可附加买卖价差的一半作为隐性成本。

#### 8.2.5 订单超时与自动撤单
订单携带 `timeout`（分钟数），超时未完全成交则自动取消，产生 `CancelEvent`。

### 8.3 撮合引擎工作流程
```
遍历订单队列所有ACTIVE订单：
  if 未到延迟时间: 跳过
  if 已超时: 取消，发送CancelEvent
  if 市价单: 全部成交，加冲击成本
  if 限价单: 检查触及，计算概率P
      r = random(0,1)
      if r < P: 成交(部分成交)
      else: 保留
更新账户，产生FillEvent/PartialFillEvent
```

### 8.4 策略如何应对成交不确定性
策略通过回调处理反馈：
- `on_fill` / `on_partial_fill`：调整预期，处理部分成交后的仓位管理。
- `on_order_cancelled`：评估是否重新下单，可能调整价格。
- 资金管理：策略应区分“可用资金”和“冻结资金”，基类提供 `self.portfolio.cash` 和 `self.portfolio.frozen_cash`，避免超额下单。
- 防御性设计：避免对单一订单完全成交的硬依赖，将部分成交视为常态。

### 8.5 从回测到实盘的校准闭环
- 回测与模拟阶段推荐使用悲观参数进行压力测试。
- 仿真与实盘积累的真实成交数据（延迟分布、成交概率、滑点）可反哺回测模型参数，实现持续校准。
- 每日复盘可自动修正撮合参数，形成“实盘→模型优化→回测验证”的良性循环。

## 9. 风险控制与资金管理

### 9.1 分层风控体系
- **策略级**：单标的仓位上限、单日最大亏损、日内交易次数限制、连续亏损暂停等。
- **全局级**：总账户保证金占用率（期货）、多币种净敞口（统一折基础币种）、跨品种关联风险限制、极端事件强制降仓。
- **订单预检查**：资金是否足够（含冻结部分）、标的是否停牌或涨跌停、是否在黑名单中。

### 9.2 资金模型
- 多币种支持，汇率定期更新。
- 不同市场结算规则（T+0/T+1/T+2）通过模拟冻结资金与可用资金的时间变化体现。
- 期货逐日盯市、保证金制度实现。

## 10. 五阶段演进路线

### 第一阶段：严格历史回测验证
- 实现数据读取、事件循环、撮合引擎、基础风控。
- 提供小时级均线交叉和日频动量示例策略。
- 输出完整绩效报告与逐笔成交明细。
- 配置文件驱动，命令行一键运行。

### 第二阶段：模拟盘跟踪验证
- 实现增量回放模式：每日追加新数据，从头流式回放至最新，得到模拟盘绩效。
- 可选断点续算提高效率。
- 采用保守撮合参数，评估实盘可行性。

### 第三阶段：信号参考输出
- 引擎切换为近实时模式（`tail` 行情文件）。
- 策略订单转化为可读信号，推送至Web或即时通讯。
- 开发人工审核界面，记录实际成交，统计信号准确度。

### 第四阶段：间隙式仿真验证 + 实盘数据复盘修正 + 后训练调优
- 间隙式仿真：非交易时段接入券商仿真环境（SimNow、模拟交易）运行策略。
- 实盘数据回流：将仿真/实盘成交数据注入回测，修正撮合模型。
- 后训练调优：Optuna参数搜索，MLflow管理ML模型，优化过程全部在严格回测中完成。
- A/B测试：新参数/模型在仿真环境与当前版本并行运行，达标后升级。

### 第五阶段：全自动实盘运行
- 切换实时行情和真实券商API。
- 启用全套生产级风控和监控，支持人工紧急干预。
- 初期小规模试运行，并行影子账户对比验证。
- 每日收盘归档数据，自动触发第四阶段优化流水线。

## 11. 技术栈与工程化保障
